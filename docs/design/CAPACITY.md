## 1. 单副本吞吐

| 并发 | 请求数 | RPS | p50 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|
| 1 | 1738 | **144.8** | 6.7 | 8.2 | 8.8 | 14.1 | 58.0 |
| 5 | 1332 | 110.7 | 46.7 | 60.0 | 62.6 | 71.0 | 87.1 |
| 10 | 1170 | 97.0 | 106.3 | 134.0 | 139.3 | 207.3 | 226.2 |
| 20 | 1346 | 112.1 | 189.4 | 219.6 | 228.3 | 243.9 | 309.8 |
| 40 | 1389 | 114.8 | 355.5 | 442.2 | 494.2 | 512.1 | 552.4 |

（单位：延迟 ms）

### 读法

**吞吐在 97–145 RPS 之间平台化，并发从 1 加到 40 只增加延迟不增加吞吐。**

延迟随并发近似线性增长（6.7 → 355），说明请求在**排队**而不是并行。
这是 CPython 的 GIL 决定的：单进程里 CPU 密集段无法并行，
`scripted` 适配器虽然不调网络，但 FastAPI 的请求处理、Pydantic 校验、
以及 Gateway/Loop 的 Python 代码都是 CPU 时间。

**结论：单副本吞吐上限约 145 RPS，加并发无益。要更高吞吐只能加副本或加 worker。**

## 2. 横向扩展

2 个副本、同一台机器、各 20 并发、同时压：

| 副本 | RPS | p50 | p95 | p99 |
|---|---|---|---|---|
| A | 95.7 | 205 | 311 | 380 |
| B | 96.8 | 207 | 301 | 358 |
| **合计** | **192.5** | — | — | — |

对比单副本 20 并发（112 RPS）：**1.72× 扩展率**（理想 2×）。

同一台机器上两进程争抢 CPU，拿不到线性扩展是预期的。真实部署里
副本分散在不同节点，扩展率应更接近线性。

### 2.1 本机 10 核（早期）

`scripts/bench_multiworker.sh`，wrk 4.2.0，每档 20 秒 × 2 轮取均值。

#### 主矩阵（`-t8 -c128`）

| 配置 | RPS（两轮） | p50 | p99 | 服务端 CPU | 客户端 CPU |
|---|---|---|---|---|---|
| 1 worker | **2,247**（2238/2256） | 55ms | 83-135ms | **109%**（1 核） | 4% |
| 4 worker | **6,681**（6570/6793） | 15-18ms | 69-116ms | **407%**（4.1 核） | 14% |
| 8 worker | **8,068**（8546/7590） | 16ms | 56-132ms | **700%**（7.0 核） | 14% |

**多 worker 有效：4 worker = 2.97×，8 worker = 3.59×。**

#### 瓶颈是 CPU，不是锁

三条证据：

1. **单 worker 在四个并发档位下吞吐恒定**（`-t1/c16` 2298 → `-t16/c256` 2143 RPS），
   只有 p50 从 6ms 涨到 112ms —— 典型的单核饱和形态。
2. **服务端 CPU 严格等于核数 × 100%**（1w=1 核、4w=4.1 核、8w=7 核）。
   若进程间存在串行化点，CPU 会停在 1-2 核而吞吐不涨。
3. **逐 PID 探针**：4 worker 各占 100%/98%/99%/100% 单核 —— 负载均匀，无空闲 worker。

所以"一个 worker 困在一个核上"是 CPython GIL 的结果，不是本仓的锁设计问题。

#### 每核产出随 worker 数衰减

| worker | 每核 RPS | 相对单核 |
|---|---|---|
| 1 | 2,250 | 100% |
| 4 | 1,630 | 72% |
| 8 | 1,150 | 50% |

原因：整机只有 10 核，压测端也在这台机器上。8 worker 时服务端 7 核 + wrk 1.5 核
+ 已知外部负载（ollama / node / VPN），整机先饱和。**8 worker 的 3.59× 不是服务端上限。**

#### 压满需要多少客户端

| 场景 | 需要的压测能力 |
|---|---|
| 单 worker（2,250 RPS） | 20+ 个旧 `loadtest.py` 进程，或 **1 个 wrk** |
| 4 worker（6,700 RPS） | 60-70 个旧进程，或 **1 个 wrk**（CPU 仅用 14%） |
| 8 worker（8,000 RPS） | 约 80 个旧进程，或 1 个 wrk |

**一个 wrk 进程就够了，它的 CPU 余量有 6 倍以上。**

#### 两个操作事实

1. **饱和后加大并发无益**：单 worker 上 `-t16 -c256` 比 `-t1 -c16` 吞吐更低、p99 涨到 400ms。
2. **`uvicorn --workers` 的父进程收 SIGTERM 会卡在 `Waiting for child process` 不退出。**
   清理必须按进程树 TERM → 等 8s → KILL，再用 `lsof` 按端口兜底
   （`pgrep -f serve.py` 会漏掉 `multiprocessing.spawn` 的子进程 —— 我自己就漏过两次）。

#### 多 worker 的语义代价

| 项 | 单 worker | 多 worker |
|---|---|---|
| 限流窗口 | 进程内，准确 | **各进程一份**，实际阈值 × N |
| 租户配额 | 进程内 | 同上 |
| `audit_log` | 一份 | 各进程一份 |
| workflow 状态 | 一份 | 各进程各管自己提交的 |
| `/metrics` | 完整 | **只有一个 worker 的数据** |

**多 worker ≈ 多副本部署，只是少了一个反向代理。** 要用它就必须同时开
`AGENT_RUNTIME_RATE_LIMIT_DISTRIBUTED=1` + 共享 Redis，否则限额会放大 N 倍。

### 2.2 完整扩展曲线（64 核）

本机只有 10 核，测不到 8 worker 以上。用一台 **64 核 x86** 的机器跑服务端
（第 8 节那台），wrk 同容器 loopback（RTT < 0.1ms），逐档重启服务：

| workers | RPS | 倍数 | 错误 |
|---|---|---|---|
| 1 | 329 | 1.0x | 0 |
| 2 | 640 | 1.9x | 0 |
| 4 | 1,347 | 4.1x | 0 |
| 8 | 2,967 | 9.0x | 0 |
| 16 | 6,754 | 20.5x | 0 |
| 32 | 16,280 | 49.4x | 0 |
| 48 | 21,106 | 64.1x | 0 |
| 56 | **21,482** | **65.3x** | 0 |
| 64 | 21,351 | 64.9x | 0 |

**平台期在 48-56 worker 之间，约 21,500 RPS。** 64 档只起了 54 个 worker
（系统进程 + 压测端也要核），吞吐反而略降 —— 这是整机饱和，不是服务端退化。

#### 两个反直觉的地方

**① 超线性扩展（16 worker = 20.5x 单 worker）。**

单 worker 只有 329 RPS，8 worker 达到 9x。原因不是"多 worker 有魔法"，
而是**单 worker 时压测端压不满**：wrk 8 线程对着一个 Python 进程，
请求全卡在同一个 GIL 上；进程多了，请求才能真并行。

**② 这里的单核数字（329 RPS）和本机（2,247 RPS）差 6.8 倍。**

同一份代码，差异来自环境不是代码：

| | 本机 | 64 核服务器 |
|---|---|---|
| CPU | Apple M5 | 服务器 x86 |
| Python | 3.14.3 | 3.12.3（容器） |
| 文件系统 | APFS | overlayfs（容器） |
| 单核 RPS | 2,247 | 329 |

**所以"每 worker 多少 RPS"这个数字不能跨机器引用**，能跨机器引用的是
**扩展比**：多 worker 接近线性，直到整机饱和。

#### 这解决了之前的一个疑问

早先记录"8 worker = 6,911-8,068 RPS"，那是**本机 10 核的上限**，不是服务端上限。
本机压测端和服务端抢同一批核，测不出更高。这次用 64 核验证：
**同等条件下能到 21,500 RPS**，是之前记录的 2.7 倍。

#### 这个数字的适用边界

上述 RPS 是**内置 `scripted` 桩模型**的结果（纯 CPU、无网络），代表
"单回合服务端 CPU 成本"的天花板场景。**接真实模型后每回合变成网络等待
（实测单次 p50 2672ms，见上节），同 CPU 能撑的并发会大得多，
"每 worker 2,250 RPS"不再适用。** 但"一个 worker 困在一个核上"这个结论不变。

### 2.3 跨机器：RTT 封顶

把压测端放到**另一台机器**（243，64 核 x86，Tailscale 内网 28ms RTT），
打本机的同配置服务，得到完全不同的一组数字：

| 配置 | 本机 loopback | 跨机（Tailscale 28ms） | 差异 |
|---|---|---|---|
| 1 worker | 2,247 | **2,151** | 一致 |
| 4 worker | 6,681 | 未测 | — |
| 8 worker | 6,911 ~ 8,068 | **3,260** | **2.1-2.5× 差距** |

**单 worker 两边一致、8 worker 差 2 倍**，这条对比本身就是结论：

- 单 worker 时服务端是瓶颈（2,250 RPS 打满 1 核），网络不是 → 两边一样
- 8 worker 时服务端变快，**网络成为新瓶颈** → 跨机只有 3,260

**决定性证据**：8 worker 跨机压测时，本机服务端 CPU 只有 **271%**（8 核满应为 800%）。
服务端没吃饱，请求卡在路上。

按 Little's law 反推：`3,260 RPS × 0.31s 延迟 ≈ 1,010 个有效并发`，
而 wrk 配置了 4,096 并发 —— 说明这条链路最多只能同时保持约 1,000 个飞行请求。
加到 `c=4096` 吞吐也不涨（3,260），只是延迟从 195ms 涨到 312ms。

#### 部署含义（比 RPS 数字更重要）

**同等服务端能力，客户端离得越远，能压出的吞吐越低。**

| 网络场景 | 典型 RTT | 单个 worker 能撑满 |
|---|---|---|
| 同机 / 同宿主 | <1ms | 4 并发就够 |
| 同机房 | 0.5-2ms | 10-30 并发 |
| 跨可用区 | 10-30ms | 200-600 并发 |
| 公网跨地域 | 50-150ms | 1,000-3,000 并发 |

所以**容量规划要先问"客户端在哪"**。服务端 8,068 RPS 的能力，
在 28ms RTT 的链路上只能兑现 3,260 —— 这不是代码问题，是要加并发数或拉近距离。

### 2.4 尾延迟随 worker 数（p99 曲线）

§2.2 只回答了"吞吐能到多少"，没回答"加了 worker 尾延迟会不会变差"。
在同一台 64 核上重测（`scripts/bench_multiworker.sh`，wrk 4.2.0，每档 2 轮、
每轮 20 秒、预热 5 秒，关闭三层配额）：

| workers | c=16 p50 / p99 | c=64 p50 / p99 | c=256 p50 / p99 | 吞吐 |
|---|---|---|---|---|
| 1 | 41.9 / **184.2** ms | 165.5 / **504.4** ms | 704.0 / **1,550** ms | 324-358 RPS |
| 4 | 8.7 / **59.8** ms | 38.8 / **165.3** ms | 156.6 / **421.9** ms | 1,428-1,692 RPS |
| 8 | 未测 | 17.6 / **81.8** ms | 71.1 / **299.5** ms | 3,105-3,118 RPS |
| 16 | 未测 | 8.9 / **41.9** ms | 32.5 / **118.5** ms | 6,880-7,061 RPS |

**结论：p99 随 worker 数单调下降，没有"worker 多了尾延迟反而变差"的拐点。**
同一并发下 1 → 16 worker：c=64 的 p99 从 504ms 降到 42ms（**12×**），
c=256 从 1,550ms 降到 119ms（**13×**）。

两个值得记的细节：

- **c=16 时 4 worker 就已饱和**（1,692 RPS 是全局最高点），再加并发只增加排队：
  16 worker 在 c=64 的 p99（42ms）比 c=16 的 4 worker（60ms）还低 —— 说明
  **并发要跟着 worker 数走**，固定并发压不同 worker 数会得出"worker 没用"的错觉。
- **1 worker 在 c=256 出现超时**（17-42 个 socket timeout），4 worker 起归零。
  排队长度超过服务能力时，客户端会先看到超时而不是错误码 —— 这正是
  `docs/design/SLO.md` 里 p99 要单独设阈值的原因。


## 3. 长稳压测

### 3.1 20 分钟（早期，已被 3.2 取代）

`scripts/soak_test.py`，并发 8，每 60 秒采样。

跑了两轮，结论一致：

| 指标 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 时长 / 请求 | 20.03 min / 121,305 | 20.02 min / **137,243** |
| 成功率 | 100% | **100%** |
| RPS | 100.95 | 114.23 |
| 延迟 | p50 77 / p99 167 ms | p50 72.6 / p95 93.5 / **p99 104.6** ms |
| 线程 | 恒定 10 | **恒定 10** |
| 文件句柄 | 137 → 137 | 137 → 137（0.038/min） |
| 内存区间 | 30.5 ~ 162.0 MB | 70.2 ~ **238.3** MB |
| p99 漂移 | 109.5 → 100.3 ms | 101.0 → 103.7 ms |

#### 内存曲线的读法（这里踩过一个坑）

RSS 呈**锯齿形**：在 30MB 与 162MB 之间摆动，20 分钟内有 5 个完整周期。

第一版判据用**全点线性拟合**，得到 2.585 MB/min，判定"存在泄漏"。**这是错的** ——
锯齿形数据做线性拟合，结果取决于"末次采样恰好在峰还是谷"，是测量噪声不是信号。

正确判据是**谷值趋势**：每个 GC 周期结束后的低点在不在抬高。

第 2 轮的原始谷值：`70.2 → 85.5 → 85.1 → 87.9 → 83.1`。

直接拟合给出 **+0.80 MB/min**（一小时 +48MB），看着像泄漏。**但剔除预热期后**：

```
前 4 个采样（4 分钟）视为预热  →  稳态谷值 85.5 → 85.1 → 87.9 → 83.1
稳态斜率 -0.10 MB/min，波动仅 4.8MB
```

**这是启动阶跃，不是线性增长**：解释器缓存、连接池、sqlite page cache
在第一分钟内填满，之后持平。

这里我撤回过一个结论：第一轮用了全点线性拟合，得出 2.585 MB/min
并判"存在泄漏" —— 那是把锯齿的峰值当成了趋势。最终判据改为
**稳态谷值斜率**，并明确剔除预热。

**决定性证据**：负载停止后 RSS 回落到 **6.2 MB**（第一轮实测）。
真泄漏不会还回去。

#### 峰值要写进容量规划

| | 值 |
|---|---|
| 稳态内存 | **85MB**（第 2 轮均值） |
| 峰值（分配尖峰） | **238MB** |
| 停止负载后 | 6MB |

按副本数规划内存时用**峰值 238MB**，不是稳态 85MB。留 1.5 倍余量 → 每副本约 350MB。

### 3.2 长稳 150 分钟（最终）

之前只跑过 20 分钟。这次跑满 **150 分钟**，103 万请求，回答"数小时级会不会泄漏"。

| 指标 | 值 |
|---|---|
| 时长 / 请求 | **150.08 分钟** / **1,036,418** |
| 成功率 | 1,036,416 × 200 + **2 × 502**（0.0002%） |
| RPS | 115.09 |
| 延迟 | p50 **72.6** p95 **91.7** **p99 101.8** ms |
| 线程 | **恒定 10**（75 次采样全一致） |
| 文件句柄 | 137 → 137（斜率 **-0.002**/min） |
| p99 漂移 | 首段 98.6 → 末段 **101.4** ms（未恶化） |

#### 内存：均值稳定，峰值在长

| 阶段 | 均值 | 最低 | 最高 |
|---|---|---|---|
| 前段（2-50min） | 101.3MB | 55.2 | 268 |
| 中段（52-100min） | **101.3**MB | 60.2 | 346 |
| 后段（102-150min） | **97.1**MB | 66.4 | **487** |

**均值没涨（甚至略降），但峰值从 268MB 长到 487MB。**

结论：**不是泄漏**。泄漏的特征是每次 GC 后剩下的更多 → 均值抬升。这里均值
平坦，说明回收是彻底的；峰值增长更像是 GC 周期变长（对象多了，触发间隔变长，
两次回收之间堆得更高）。

#### 判据改过一次，理由值得记

三种方法都拿这组真实数据验证过：

| 方法 | 结果 | 问题 |
|---|---|---|
| 全点线性拟合 | -0.109 MB/min（负） | 被峰值噪声主导，结果取决于末次采样落在峰还是谷 |
| 谷值斜率 | +0.68 MB/采样（像泄漏） | t=20min 的偶发低谷 55.2MB 拉低起点；谷值序列本身不单调 |
| **分阶段均值** | 101.3 → 97.1（比值 0.96） | **采用这个** |

长序列里偶发低谷/峰值会被前两种方法放大成假信号。阶段均值对单个异常采样
不敏感，才是"稳态有没有涨"的正确问法。阈值设 1.25（允许 25% 波动）。

#### 2 个 502

103.6 万请求里有 2 个 502，服务端日志的 `UNRECOVERABLE` 计数是 **0**
（验证过：`grep -c UNRECOVERABLE` = 0），所以不是 Loop 层的不可恢复错误。
最可能是压测端某个瞬间的连接问题。0.0002% 的失败率，记录在案但不作为缺陷。

#### 跑满 150 分钟本身踩了一个坑

前两次尝试都在 ~50 分钟时**服务被 SIGTERM 优雅关闭**（日志有完整的
`server.drained` → `server.stopped` 序列，不是崩溃）。

根因：用 `nohup ... &` + `disown` 启动时，非交互 shell 里 `disown` 会失败，
进程仍留在会话里，shell 退出后被连带清理。

修法：用 `subprocess.Popen(..., start_new_session=True)` 启动（等价 `setsid`），
彻底脱离控制终端。**这一条对任何"要跑很久的本地进程"都适用。**

### 3.3 12 小时长稳：抓到一条线性增长（已修）

150 分钟那轮内存是平的，所以计划"跑满 12 小时"时预期只是拉长时间。
**第一轮 12 小时（旧构建）在 4 小时处就露了**：

| t | RSS | 请求 | p99 |
|---|---|---|---|
| 1 min | 191 MB | 19k | 48.5 ms |
| 33 min | 499 MB | 674k | 46.0 ms |
| 242 min | **2,485 MB** | 4.91M | 56.7 ms |
| 258 min | **2,635 MB** | 5.23M | 62.3 ms |

**斜率 ≈ 9.5 MB/min ≈ 0.5 KB/回合，线性、无平台期。** 延迟和线程数完全正常
（77 线恒定、p99 在 40-60ms 带内），所以只看 150 分钟、只看 p99 的话，这条
增长永远发现不了 —— 这正是"长稳要跑够久"的意义。

根因（`core/observability.py`）：`JsonLogger._records` 是一个**无上界**的
`list[dict]`，每次 `log()` 都 append 一条，供 `records()` 做内存副本。每回合
都会写 `turn.completed`，于是这份"排障用的最近记录"实际上等于"全部回合"。
MacBook 上同样复现（3.35 MB/min ÷ 6.7k req/min ≈ 0.5 KB/回合）。

修法：改成 `deque(maxlen=records_limit)`（默认 1000 条，约 0.5MB）。日志本身
一条不少 —— 走 sink 的那份不受影响，被限的只是内存副本。

修后同机同负载：

| t | RSS | 请求 |
|---|---|---|
| 2 min | 183.3 MB | 40k |
| 4 min | **183.3 MB** | 80k |

**80k 请求内 RSS 一动不动。** 12 小时（修复后）的长稳正在 243 上跑，用来确认
整个时长内是平台而不是延迟出现。

## 4. 上游 LLM 延迟

### 4.1 云端 deepseek-flash

`scripts/real_llm_capacity.py`，deepseek-flash，12 次调用，并发 3。

| 指标 | 值 |
|---|---|
| 单次延迟 | p50 **2672ms**，p95 3742ms，p99 **3805ms** |
| 抖动 | stdev 599ms（占 p50 的 22%） |
| token | in 72 / out 120 每次，**缓存命中率 0%** |
| 推算回合（4-6 步） | p50 **10.7 ~ 16.0 秒**，p99 **15.2 ~ 22.8 秒** |

**结论：接真实模型后，本层的排队开销（< 1 秒）相比上游（10-40 秒）可以忽略。**
容量规划要按上游定，不是按这份文件里的 145 RPS。

缓存命中率 0% 是因为测试每次发新 prompt 且无共享前缀。真实多轮场景里
system prompt 固定，命中率会高得多 —— 那正是 `Usage.billable()` 存在的理由。

### 4.2 Strata 本地（2×T4）

第一组是 deepseek-flash（云端网关）。另一组是**本地部署**：Strata 引擎跑
`qwen3.8-flash-next-q2_0`（Q2 量化，32K 上下文，支持图文），硬件 2×Tesla T4。

`scripts/real_llm_capacity.py --calls 10 --concurrency 1 --warmup 2`：

| 指标 | 值 |
|---|---|
| 单次延迟（剔除冷启动） | p50 **4,266ms**，p95 5,720ms，p99 5,934ms |
| 抖动 | stdev 691ms（p50 的 16%） |
| 输出速度 | 约 20 tok/s（120 token 输出） |
| 推算回合（4-6 步） | p50 **17.1 ~ 25.6 秒** |
| 缓存命中 | **恒为 0**（该引擎不报 `prompt_cache_hit_tokens`） |

#### 冷启动必须剔除

前两次调用 **13.8 秒 / 8.4 秒**，稳定后 1.4-2.1 秒（短输出场景）。
不剔除的话 p50 被拖到 **16.7 秒**，结论差 4 倍。

所以脚本加了 `--warmup N`：前 N 次不计入统计。理由：首次请求包含权重加载与
KV cache 构建，是**一次性成本**，不是服务能力。任何压测都要区分这两者。

#### 端到端回合验证

用我这套运行时接 Strata 跑了一个真实回合（2 步，42 秒）：

```
phase=DONE  term=DONE  steps=2
工具调用: [('get_metrics', 'ok')]
text: api 服务的 p99 指标为 **3120 ms**，超过 1 秒，说明服务劣化。
      error_rate: 0.021 / qps: 1450
```

**关键点：模型正确地把我的纯文本工具描述转成了 `tool_calls`** ——
本仓不用原生 `assistant.tool_calls` 协议（见 STATUS.md 的取舍说明），
而是把工具渲染成文本。这次实测证明这条路径在真实模型上可用：
adapter 收到 `get_metrics(service='api')`，Loop 执行后模型正确引用结果。

### 4.3 vLLM 本地 27B（4090）

`Qwen3.8-27B-W4A16-AWQ-GPTQ`（4bit 量化），vLLM 0.32，单张 4090（48GB）。

#### 启动参数决定能不能用

这台机器上踩了五个坑，每个都让容器起不来：

| 现象 | 根因 | 解法 |
|---|---|---|
| `can't start new thread` | 容器缺 `--privileged` | 原容器就是 `Privileged: true`，漏了 |
| `CPU dispatcher tracer already initlized` | numpy 在受限 cgroup 下初始化失败 | 同上，加 `--privileged` 即可 |
| `Free memory ... less than desired utilization` | `0.99 × 48GB` 超过物理可用 | 降到 **0.88**（模型权重 25.22 GiB，要留 KV 空间） |
| `No available memory for the cache blocks` | util 太低，KV 空间为 0 | 同上，0.88 是这台的甜蜜点 |
| `"auto" tool choice requires --enable-auto-tool-choice` | vLLM 默认不接受 `tools` 参数 | 加 `--enable-auto-tool-choice` |
| `tool_calls` 恒为 None，`finish=stop` | parser 与模型的模板格式不匹配 | 该模型用 `<tool_call><function=` 格式 → **`--tool-call-parser qwen3_xml`**（不是 `hermes`） |

**最值得记的是最后两条**：vLLM 显示 200 OK、能正常对话，但 `tools` 参数
静默失效 —— 只有加对 parser 才真的产出 `tool_calls`。用 `hermes` 时模型
输出了思考但没有结构化调用，`finish_reason` 是 `stop` 而不是 `tool_calls`。

#### 实测

`strip_reasoning` 之后，单次调用 **4.5-4.8 秒**（稳态，in=321 / out=64）。
完整回合（2 步）：

```
phase=DONE  term=DONE  steps=2  16.3 秒
text: api 服务 p99 = **3120ms（约 3.12s）**，已超过 1 秒阈值，**确认劣化**。
      其他指标：error_rate 2.1%，qps 1450。
工具调用: [('get_metrics', 'ok')]
```

#### 推理模型的思维链必须剥

这颗模型是推理模型，`content` 长这样：

```
用户问"2+2等于几？只回答数字。" 需要只回答数字。答案是4。
</think>

4
```

而 `message["reasoning"]` 是 **None** —— 服务端没配 `--reasoning-parser` 时
vLLM 不会单独给这个字段。不处理的话：

| 后果 | 说明 |
|---|---|
| 把独白当答案 | 用户读到"用户问……需要只回答数字"，不是答案 |
| 污染 history | 下一轮模型看到自己的思维链当前文，判断会漂 |
| 回合文本失去检索价值 | 存进 Memory 的是内心独白 |

`OpenAICompatAdapter` 现在有 `strip_reasoning=True`（默认开）：剥离
`</think>` / `</thinking>` / `[/THINK]` 等标记之前的内容。

**保守规则**：标记之后为空时**保留原文** —— 推理吃光 max_tokens 时
`content` 可能只剩标记前的内容，剥掉会得到空字符串，把"模型没答完"
变成"模型答了空"，那是更糟的失败。

实测同一请求：

```
strip_reasoning=True : '4'
strip_reasoning=False: '用户问"2+2 等于几？只回答数字。" 需要只回答数字。答案是4。\n</think>\n\n4'
```

## 5. 缓存计价

### 5.1 真实结论：缓存生效，但 usage 不报

这是本节最有价值的一条 —— 不是"没测"，是**测了，得到否定结论**。

实验：在 vLLM 0.32 上跑 `Qwen3-VL-Embedding-2B`（标准 attention 架构，
不是 Mamba 混合），开 `--enable-prefix-caching`，发三次**完全相同**的长 prompt。

结果：

| 观测点 | 值 |
|---|---|
| `/metrics` 的 `prefix_cache_hits_total` | 0 → **1,248** |
| `/metrics` 的 `prompt_tokens_cached_total` | **1,856** |
| `usage.prompt_tokens_details` | **null** |
| `usage.cached_tokens` | **不存在** |

**缓存确实命中了（metrics 有硬数字），但 vLLM 完全不通过 usage API 暴露。**

完整的 usage 长这样：

```json
{"prompt_tokens": 624, "total_tokens": 632, "completion_tokens": 8,
 "prompt_tokens_details": null, "completion_tokens_details": null}
```

### 5.2 这意味着什么

`Usage.billable()` 的折扣逻辑在 **vLLM 上游无法生效** —— 不是代码写错，
是上游不给数据。三组上游都验证过：

| 上游 | usage 报缓存？ | metrics 报缓存？ |
|---|---|---|
| deepseek-flash（云端网关） | 报 `prompt_cache_hit_tokens` | — |
| Strata（2×T4） | 不报 | 无此指标 |
| vLLM 0.32（4090） | **不报（null）** | **报**，但只在聚合指标里 |

**所以 `Usage.billable()` 在云端网关上可用、在 vLLM 上不可用。**

### 5.3 兜底方案：从 `/metrics` 读累计值

`adapters.openai_compat.scrape_prefix_cache_tokens(metrics_url)` 读 vLLM 的
`prompt_tokens_cached_total`：

```python
from adapters.openai_compat import scrape_prefix_cache_tokens

before = scrape_prefix_cache_tokens("http://HOST:PORT/metrics", model_name="vlchat")
...跑一批请求...
after  = scrape_prefix_cache_tokens("http://HOST:PORT/metrics", model_name="vlchat")
cached = after - before          # 这批请求的缓存命中总量
```

**实测（243 上的真实 vLLM）**：

```
抓取前 2464 → 抓取后 3072，本次增量 608
billable 全价 624 → 用增量后 77    ← 省 87.7%
```

**故意不做成请求级自动兜底**：请求前后各抓一次 metrics 求差值，并发下无法
归属到具体请求，只能串行化那个窗口 —— 那会把高并发吞吐压垮，代价远大于收益。
所以只给累计值，由调用方按时间窗口求增量。

抓取失败一律返回 0（fail-open）：观测面不该成为业务的单点。

### 5.4 为什么不做请求级自动兜底

两次实测 `cached` 恒为 0，Strata 与 vLLM（未开 `--enable-prefix-caching`）
都不报这个字段。所以 **`Usage.billable()` 的缓存折扣逻辑只被单元测试覆盖，
没有真实上游数据验证**。这一条如实记在这里，不假装验过。

## 6. 定 SLO 的依据

按单副本 145 RPS、2 副本 192 RPS 的实测，给出**保守**的 SLO 建议值：

| 指标 | 目标 | 依据 |
|---|---|---|
| 可用性 | 99.9% / 月 | 需多副本 + 健康检查（`/readyz`） |
| 回合延迟 p95 | < 500ms | 并发 40 时实测 494ms，留余量取并发 20 的 228ms |
| 回合延迟 p99 | < 800ms | 并发 40 实测 512ms |
| 错误率 | < 0.1% | 压测中 0 错误（未触配额时） |

## 8. 存储

### 8.1 会话跨副本

**之前做不到，现在能了。** 根因是 `_make_store()` 只支持
`memory / sqlite / file`，而这三种是**单机文件** —— 多副本各写各的，
A 写的轮次 B 读不到。`RedisStore` 早已实现却没有接进这个分支。

补上 `AGENT_RUNTIME_STORE=redis` 之后实测：

```
副本 A 写第1轮 → turn_index=1
副本 B 写第2轮 → turn_index=2
副本 A 写第3轮 → turn_index=3
```

`turn_index` 跨副本连续，Redis 里存有完整 6 条 history（3 轮 × 2）。

### 8.2 sqlite 写入争用

副作用 checkpoint 是**写**。高并发回合下所有 worker 都在抢写锁，这道锁的代价
需要量化，否则"用 sqlite 就够了"是个没根据的判断。

#### 同进程多线程写

| 写者 | 总数 | 写/s | p50 | p99 | 失败 |
|---|---|---|---|---|---|
| 1 | 40 | **15,580** | 0.05ms | 0.18ms | 0 |
| 4 | 160 | 13,587 | 0.04ms | 3.87ms | 0 |
| 8 | 320 | 11,899 | 0.04ms | 5.07ms | 0 |
| 16 | 640 | **5,020** | 0.04ms | 39.96ms | 0 |

**吞吐随并发下降（3 倍），但 p50 不动、p99 从 0.18ms 涨到 40ms。**
这是 GIL + 写锁排队：单次写本身很快（0.04ms），排队时间才是成本。

**零 `database is locked`** —— `busy_timeout` 足够，争用表现为排队而不是失败。

#### 多进程写同一文件（多副本共用 sqlite 的真实形态）

| 进程 | 成功 | 失败 | 写/s | 相对单进程 |
|---|---|---|---|---|
| 1 | 30 | 0 | 375 | 1.00x |
| 2 | 60 | 0 | 619 | 1.47x |
| 4 | 120 | 0 | **1,212** | **3.07x** |

**零写失败，且吞吐随进程数增长到 3.07x（线性 4x）。** sqlite 的多进程写
**基本可用**，争用不严重 —— 这一条与我的预期相反，我原本以为会是串行的。

这里我又踩了一次"预设污染报告"的坑：脚本第一版把结论写死成
"吞吐不随进程数增长 → 写锁串行"，而实测是 3.07x 增长。已改成**从数据推结论**。

#### 但仍不建议多副本共用 sqlite（与吞吐无关）

1. **网络文件系统上 WAL 不成立**：NFS / SMB / 部分 FUSE 的锁语义会让 WAL 失效，
   而这时不会报错，只在并发写时偶发**丢数据**
2. **单文件是单点**：一个副本的磁盘故障带走全部状态
3. **备份要停写**：sqlite 备份需要 `backup API` 或停写快照；Redis 可做主从

所以选 `STORE=redis` 的理由是**故障域与运维语义**，不是吞吐。
单副本用 sqlite 完全没问题：实测 5,000 写/s 相对单副本 100 RPS 的回合频率
（每回合 1-5 次 checkpoint）有两个数量级的余量。

## 附录 A：测量方法

这份文档里每一个数字都是实测的。同样重要的是**怎么测**——下面几条是踩过坑之后的纪律。

### A.1 压测工具的选择

| 工具 | 天花板 | 用途 |
|---|---|---|
| `scripts/loadtest.py`（单进程 httpx） | ~110 RPS | **不要用来测吞吐**，只能测功能 |
| `wrk`（C，每线程独立 epoll） | 21,500+ RPS | 所有吞吐数字都用它 |

单进程 Python 压测器受 GIL 限制，量到的永远是它自己的上限。这一点让第一版
文档错了 15 倍（见附录 B.1）。

### A.2 冷启动必须剔除

前 N 次请求包含模型加载、KV cache 构建、torch.compile 等一次性成本。

| 上游 | 冷启动 | 稳态 | 倍数 |
|---|---|---|---|
| Strata（2×T4） | 13.8s / 8.4s | 1.4-2.1s | ~7x |
| vLLM 27B（4090） | 78s | 4.5-4.8s | ~17x |

不剔除会把 p50 从 4.3 秒拖到 16.7 秒。`real_llm_capacity.py` 因此有 `--warmup N`。

### A.3 内存判据：用阶段均值，不用拟合

| 方法 | 150 分钟数据的结果 | 问题 |
|---|---|---|
| 全点线性拟合 | -0.109 MB/min（负） | 峰值噪声主导，取决于末次采样落在峰还是谷 |
| 谷值斜率 | +0.68 MB/采样（像泄漏） | 单个偶发低谷拉低起点；谷值不单调 |
| **阶段均值** | 101.3 → 97.1（比值 0.96） | **采用**，对单个异常采样不敏感 |

RSS 在 55-487MB 之间锯齿摆动是 CPython 分配器行为（不立刻还给 OS）。
**真泄漏的特征是均值抬升**，不是峰值波动。

**决定性验证**：停掉负载后 RSS 回落到 6MB。真泄漏不会还回去。

### A.4 区分"服务端饱和"与"网络瓶颈"

跨机器压测时，8 worker 只跑到 3,260 RPS，看着像服务端上限。但：

```
服务端 CPU 只有 271%（8 核应为 800%）
→ 请求在路上，不在处理
```

按 Little's law：`3,260 RPS × 0.31s ≈ 1,010 个有效并发`。把并发从 1,024
加到 4,096，吞吐不变、只有延迟涨——证实是链路饱和。

**判据：看服务端 CPU 是否打满，不能只看 RPS。**

### A.5 长时间后台进程要 `start_new_session`

前两次 150 分钟长稳都在 ~50 分钟时被 SIGTERM 杀掉（日志有完整的
`server.drained` → `server.stopped`，不是崩溃）。

根因：`nohup ... &` + `disown` 在**非交互 shell** 里 `disown` 会失败，
进程留在会话里，shell 退出被连带清理。

修法：

```python
subprocess.Popen([...], start_new_session=True)   # 等价 setsid(2)
```

**任何要跑很久的本地进程都适用。**

### A.6 清理要按 PID，不要 `pkill -f`

`pkill -9 -f "soak_test"` 会匹配到**执行它的那个 shell**（命令行里含这个字符串），
把自己杀掉。

正确做法：

```bash
for pid in $(ps aux | grep "[s]oak_test.py" | awk '{print $2}'); do
  kill -9 $pid
done
```

方括号技巧（`[s]oak`）让 grep 不匹配自己。

## 附录 B：被推翻的结论

保留这些是因为**它们本身是"怎么测错"的证据**。

### B.1 吞吐数字错了 15 倍（2026-11-26）

**当时的结论**：单副本 145 RPS 平台化，多 worker 无提升。

**为什么错**：用单进程 `httpx.AsyncClient` 压测，它自身天花板 ~110 RPS，
只有服务端的 1/20。量到的是压测端。

**更正后**：单 worker 2,247 RPS，4 worker 6,681 RPS（2.97×），
56 worker 21,482 RPS。

**教训**：**压测工具的上限必须先验证**，否则它给出的每个数字都是错的。

### B.2 内存"泄漏"是误判（2026-11-26 第一次）

**当时的结论**：RSS 斜率 2.585 MB/min，存在泄漏。

**为什么错**：对锯齿形数据做全点线性拟合，结果取决于末次采样落在峰还是谷。

**更正后**：剔除预热后稳态斜率 -0.10 MB/min，无泄漏。

**教训**：**判据要匹配数据形状**。锯齿形数据看谷值或阶段均值，不能看全点斜率。

### B.3 "多 worker 无效"（2026-11-26，同 B.1）

**当时的结论**：4 worker 与单 worker 都是 111-131 RPS，判定"多 worker 无效"。

**为什么错**：同 B.1，压测端先饱和。

**更正后**：4 worker = 2.97×，56 worker = 65.3×。

**教训**：**"没有提升"这个结论在弱压测下不可信**。先排除测量工具的限制。

### B.4 缓存计价"测不了"改成了"不可用"（2026-11-27）

**当时的结论**：三组上游都不报 cache hit，所以"没验证"。

**更正后**：不是"没验证"，是**有证据的否定结论**——缓存确实命中
（`/metrics` 有 1,856 tokens），但 vLLM 的 usage API 报 `null`。

**教训**："测不了"和"测了但不支持"是两件事。后者需要证据，也需要给出兜底方案。
